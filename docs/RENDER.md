# Deploying UniLodge on Render (free)

This is the current deployment path. It uses a teammate's Render workspace so
it is separate from the suspended account.

The repo contains a Blueprint (`render.yaml`) that creates everything in one
apply: a Docker web service and a PostgreSQL database, both in Frankfurt.

> Free instances are for demos, not production. Read the limits below before
> relying on the URL for anything important.

## Free-plan limits that matter here

| Limit | Value | What it means |
| --- | --- | --- |
| Web instance | 0.1 CPU, 512 MB RAM | Slow cold starts, tight memory |
| Idle behaviour | Spins down after 15 minutes without traffic | First visit takes 1-2 minutes |
| Instance hours | 750 per workspace per month | Do not add keep-alive pingers or a second free service |
| Bandwidth | Included monthly amount | Fine for a demo; overage suspends free services without a card |
| Free Postgres | 1 GB, **expires 30 days after creation** | Plan for this; see section 8 |
| Builds | Monthly pipeline minutes | The first Docker build takes several minutes |
| Outbound SMTP | Ports 25/465/587 blocked | Use `MAIL_MODE=console` and read OTP codes from logs |
| Persistent disk | Not available on free | Uploaded files are lost on restart |

## 1. Deploy with the Blueprint

1. Sign in to the teammate's Render account.
2. Open this link:

   <https://render.com/deploy?repo=https://github.com/La-Pulga-001/UniLodge>

3. Connect GitHub if asked, then choose the `La-Pulga-001/UniLodge` repo and
   the `main` branch.
4. Give the Blueprint a name, for example `unilodge`.
5. Apply. Render creates `unilodge-db` and `unilodge`, builds the Docker image
   and deploys it.

The first build downloads Maven dependencies and compiles the multi-module
project. Expect roughly 5-15 minutes. The first boot then runs Flyway
migrations and seeds the demo catalogue, which adds another 1-3 minutes on the
free CPU.

The service is live when the health check at `/api/universities` passes. The
public address looks like `https://unilodge-xxxx.onrender.com`.

### If Render cannot see the repository

The repository is public, but Render's GitHub integration only lists repos the
connected GitHub account can grant access to. If it is missing:

- Add the teammate as a collaborator on GitHub
  (`La-Pulga-001/UniLodge` → Settings → Collaborators), then reconnect GitHub
  in Render, or
- Fork the repo to the teammate's GitHub account and deploy the fork. Pushes to
  the original repo will not auto-deploy in that case.

As a last resort, create the service manually: **New → Web Service → Public Git
repository**, paste `https://github.com/La-Pulga-001/UniLodge`, choose Docker,
then create the Postgres database and wire the variables from section 3 by
hand.

## 2. What the Blueprint creates

`render.yaml` defines:

- `unilodge-db`: free PostgreSQL 17 in Frankfurt, database `unilodge`, user
  `unilodge_app`
- `unilodge`: free Docker web service in Frankfurt, health check
  `/api/universities`, auto-deploy on every commit to `main`

The database variables are bound with `fromDatabase`, so the app always gets
the current host, port, database, user and password. `JWT_SECRET` is generated
once by Render and kept stable.

## 3. Environment variables

The Blueprint sets these automatically:

| Variable | Value |
| --- | --- |
| `SPRING_PROFILES_ACTIVE` | `prod` |
| `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USERNAME`, `DB_PASSWORD` | from `unilodge-db` |
| `JWT_SECRET` | generated by Render |
| `DEMO_DATA` | `true` |
| `MAIL_MODE` | `console` |
| `JAVA_TOOL_OPTIONS` | heap cap, serial GC, C1-only JIT, headless AWT |

`APP_URL` is not set. The production profile falls back to
`RENDER_EXTERNAL_URL`, which Render sets to the service's public `https://`
address, so OTP, password-reset and invitation links are correct out of the
box.

Add `APP_URL` only when you attach a custom domain (section 9).

## 6. Cold starts and performance

The free instance spins down after 15 minutes without inbound traffic. The next
request shows a Render loading page and takes about one to two minutes for this
JVM app. This is normal, not a crash.

Do **not** add an uptime pinger or keep-alive service. Keeping a free service
awake around the clock consumes the 750 monthly instance hours and is the most
common reason Render suspends free services. One service that sleeps when idle
stays comfortably inside the allowance.

If the service is killed with exit code 137 or logs `OutOfMemoryError`, the
512 MB limit is too tight. Options, in order:

1. Lower the heap: change `JAVA_TOOL_OPTIONS` to
   `-XX:MaxRAMPercentage=50 -XX:+UseSerialGC -XX:TieredStopAtLevel=1 -Djava.awt.headless=true`
2. Upgrade the web service to the paid **Starter** plan (0.5 CPU / 512 MB,
   `$7/month`); the free database can stay.
3. Set `DEMO_DATA=false` to skip photo generation and seeding (loses the demo
   content).

## 7. Database, uploads and data

- Demo content and accounts live in PostgreSQL and survive restarts and
  deploys.
- Uploaded photos live in the container filesystem and are lost on every
  restart or deploy. The free plan cannot attach a persistent disk. Demo photos
  are regenerated automatically.
- Render might restart a free service or database at any time. Stateless JWT
  sessions and the managed database make that harmless.

## 8. The free database expires after 30 days

This is the one limit that breaks a long-running demo. Render deletes a free
Postgres database 30 days after creation, with a 14-day grace period to upgrade
it. There is no way to disable the expiry on the free plan.

Note the creation date in the Render dashboard and pick one option before day
30:

### Option A: upgrade the database

Change `unilodge-db` to the smallest paid plan. Data and the URL stay the same.
This is the least work if the demo must keep its accounts and listings.

### Option B: recreate the free database (data loss)

1. Delete the expired `unilodge-db` (a workspace can have only one free
   database).
2. Create a new free PostgreSQL database named `unilodge-db` in Frankfurt, or
   re-apply the Blueprint so Render recreates it.
3. If you created it manually, copy its host, port, database, user and password
   into the service's `DB_*` variables.
4. Redeploy. Flyway migrates the empty database and the demo catalogue is
   seeded again.

All real accounts and listings are lost in this option. Demo accounts return
with `Demo@1234`.

### Option C: move the database to Neon (no expiry)

Neon's free Postgres does not expire and needs no card. It is an external
database, so Render counts the traffic as service-initiated; a low-traffic demo
is fine, but avoid heavy automated access.

1. Create a project at <https://neon.tech>, region AWS `eu-central-1`
   (Frankfurt), and copy the connection string.
2. In `render.yaml`, remove the `databases:` block and change the five `DB_*`
   entries from `fromDatabase` to `sync: false`, for example:

   ```yaml
   - key: DB_HOST
     sync: false
   - key: DB_PORT
     sync: false
   - key: DB_NAME
     sync: false
   - key: DB_USERNAME
     sync: false
   - key: DB_PASSWORD
     sync: false
   ```

3. Commit and push.
4. In Render, open the service's **Environment** page and enter the Neon values.
   The host looks like `ep-xxxx-pooler.eu-central-1.aws.neon.tech`; the port is
   `5432`.
5. Redeploy. Migrations and demo seeding run against the new database.

The JDBC driver negotiates SSL automatically, so `sslmode=require` is not
needed with the discrete `DB_*` variables. If you prefer a single URL, set
`DB_URL` to
`jdbc:postgresql://<host>:5432/<database>?sslmode=require` instead.

## 9. Custom domain

1. Render Dashboard → `unilodge` → **Settings → Custom Domains**.
2. Add the domain and follow the DNS instructions. Render issues the TLS
   certificate automatically.
3. Set `APP_URL` to the new `https://` address and redeploy, so email links use
   the custom domain.

## 10. Updating the site

Every push to `main` triggers a build and deploy. To deploy without a new
commit, open the service and choose **Manual Deploy → Deploy latest commit**.
Rollbacks to the two previous deploys are available on the free plan.

## 11. Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| Deploy fails at the health check | Read the deploy log. The first boot is slow; if Flyway failed, check the database values. |
| Build fails during `mvn package` | Check the build log; the Docker context must be the repo root. |
| `OutOfMemoryError` or exit code 137 | Lower `MaxRAMPercentage`, or upgrade to Starter. See section 6. |
| `Connection refused` to PostgreSQL | The database is still provisioning, or it is not in the same region as the service. |
| Login works, but links point to localhost | `APP_URL` is set to a wrong value, or `RENDER_EXTERNAL_URL` is missing. Clear `APP_URL` or set it to the public address. |
| Everyone is logged out after a deploy | `JWT_SECRET` changed. Restore the previous value. |
| Site shows a Render loading page for a minute | Free service spinning up after idle. Expected. |
| Site shows 502 right after waking | The JVM is still starting. Wait, then reload. |
| Demo photos are missing | The filesystem was reset and the seeder is regenerating them. Reload after a minute. |
| Free database expired | See section 8. |
| All free services suspended | 750 instance hours or bandwidth exhausted, or a service-initiated traffic flag. Hours reset on the 1st; otherwise contact `support@render.com`. |
| Builds disabled for the month | Pipeline minutes exhausted. Existing deploys keep running. |

## 12. Keeping the free service alive

- Keep one free web service per workspace if possible.
- Do not use keep-alive pingers. Sleeping is what keeps the service inside the
  750-hour allowance.
- Avoid scraping or bulk image generation from the deployed instance.
- Keep an eye on **Billing → Monthly Included Usage** in the Render dashboard.
